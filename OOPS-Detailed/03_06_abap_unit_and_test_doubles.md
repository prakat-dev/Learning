## 2. The Problem (Why This Concept Matters)

**Real-World Scenario.** A pricing change must ship today. Manually testing it means creating orders in the GUI, posting, and eyeballing totals — minutes per case, easily skipped. With automated unit tests, the same rules verify in seconds on every activation.

**What Happens WITHOUT This Concept.** Logic is verified by hand, irregularly. Regressions slip in; refactoring is scary because nothing proves you didn't break anything; bugs are found in production.

**Why This Matters in SAP.** ABAP Unit is built into the platform and runs in ADT and in CI. Combined with test doubles, it lets you verify business logic without a database, RFC, or UI — fast, repeatable, and a precondition for safe refactoring of the whole OO design this curriculum builds toward.

## 3. Core Concept Explanation

**Definition.** **ABAP Unit** is the framework for automated unit tests: local test classes marked `FOR TESTING`, with test methods that arrange inputs, invoke the code, and assert results via `cl_abap_unit_assert`. A **test double** is a stand-in for a real collaborator: a *stub* (returns canned answers), a *spy* (records calls), or a *mock* (verifies expected interactions). Doubles can be hand-written or generated by `cl_abap_testdouble`.

**Key Principles:**
- A unit test is fast, isolated, deterministic, and asserts one behaviour (Given/When/Then).
- Declare risk/duration: `RISK LEVEL HARMLESS DURATION SHORT` for pure logic tests.
- Use `setup`/`teardown` for per-test fixtures; reset shared static state (Topic 2.2).
- Isolate the unit by injecting doubles (Topic 3.5) for its collaborators.

**How It Works.** ABAP Unit discovers `FOR TESTING` classes and runs each `FOR TESTING` method, calling `setup` before each. Assertions raise and mark the test failed on mismatch. Doubles replace real dependencies so only the unit's own logic is exercised.

**Why It's Designed This Way.** Isolating one unit (via doubles) makes failures pinpoint the cause, and speed makes running tests on every change practical — the two properties that make tests actually get written and run.

## 5. Code Example 1: Basic Concept

**Scenario:** A first ABAP Unit test for pure logic.

**The WRONG Way (Anti-Pattern):**
```abap
" "testing" by writing to the screen and looking:
DATA(lo) = NEW zcl_calc( ).
WRITE lo->add( 2 3 ).        " a human must read '5' and judge — not automated, not repeatable
```
**Problems with this code:**
- No assertion, no pass/fail, no automation; relies on a person looking.
- Cannot run in CI or on activation.

**The RIGHT Way (Following Best Practice):**
```abap
CLASS ltcl_calc DEFINITION FOR TESTING DURATION SHORT RISK LEVEL HARMLESS.
  PRIVATE SECTION.
    DATA mo_cut TYPE REF TO zcl_calc.        " cut = code under test
    METHODS setup.
    METHODS add_returns_sum FOR TESTING.
ENDCLASS.
CLASS ltcl_calc IMPLEMENTATION.
  METHOD setup.
    mo_cut = NEW zcl_calc( ).                " fresh instance before each test
  ENDMETHOD.
  METHOD add_returns_sum.
    " GIVEN mo_cut; WHEN add; THEN assert:
    cl_abap_unit_assert=>assert_equals(
      act = mo_cut->add( iv_a = 2 iv_b = 3 )
      exp = 5
      msg = 'add should return the sum' ).
  ENDMETHOD.
ENDCLASS.
```
**Why this is better:**
- The framework reports pass/fail automatically, every run.
- `setup` guarantees a clean fixture per test method.

**Step-by-Step Explanation:**
- `FOR TESTING DURATION SHORT RISK LEVEL HARMLESS` — declares a fast, side-effect-free test class.
- `setup` — runs before each test method.
- `assert_equals( act = … exp = … )` — the verification; mismatch fails the test.

## 6. Code Example 2: Real-World Application (isolation with a generated test double)

**Business Scenario:** Test `zcl_order_service` (which depends on `lif_order_repo`) without a database — first with a hand-written double, then with the `cl_abap_testdouble` framework, and finally verifying an interaction with a spy.

```abap
CLASS ltcl_order_service DEFINITION FOR TESTING DURATION SHORT RISK LEVEL HARMLESS.
  PRIVATE SECTION.
    METHODS total_uses_repo_handwritten FOR TESTING.
    METHODS total_uses_repo_framework   FOR TESTING.
ENDCLASS.

CLASS ltcl_order_service IMPLEMENTATION.

  METHOD total_uses_repo_handwritten.
    " A hand-written STUB implementing the dependency interface:
    DATA(lo_repo) = CAST lif_order_repo( NEW lcl_stub_repo( ) ).  " returns canned vbak
    DATA(lo_cut)  = NEW zcl_order_service( io_repo = lo_repo ).

    cl_abap_unit_assert=>assert_equals( act = lo_cut->total( '1' ) exp = CONV p( '200.00' ) ).
  ENDMETHOD.

  METHOD total_uses_repo_framework.
    " A double GENERATED by the framework for the interface — no class to write:
    DATA lo_repo TYPE REF TO lif_order_repo.
    lo_repo ?= cl_abap_testdouble=>create( 'LIF_ORDER_REPO' ).

    " Configure: the NEXT recorded call returns this value...
    cl_abap_testdouble=>configure_call( lo_repo
      )->returning( VALUE vbak( vbeln = '1' netwr = '350.00' ) ).
    lo_repo->read( '1' ).                       " ...recorded for read('1')

    DATA(lo_cut) = NEW zcl_order_service( io_repo = lo_repo ).
    cl_abap_unit_assert=>assert_equals( act = lo_cut->total( '1' ) exp = CONV p( '350.00' ) ).
  ENDMETHOD.

ENDCLASS.
```

**Detailed Walkthrough:**
- **Hand-written stub** — a small class implementing `lif_order_repo` with canned data; full control, more code.
- **`cl_abap_testdouble=>create( 'LIF_ORDER_REPO' )`** — generates a double for the interface at runtime; no stub class needed.
- **`configure_call( … )->returning( … )` then call** — the configure-then-record idiom: configure the behaviour, then call the method once so the framework binds that behaviour to those arguments.

**How This Works in Practice.** Hand-written doubles suit simple or highly specific cases; the framework shines when an interface is large or you need argument matching and verification. Both rely on the unit accepting its dependency by injection (Topic 3.5).

**Why This Implementation.** Isolating the service from the database makes the test instant and deterministic, and pins any failure to the service's own logic.

## 7. Code Example 3: Common Mistakes

**Mistake #1: Tests that hit the real database/RFC.**
```abap
METHOD total_is_correct FOR TESTING.
  DATA(lo) = NEW zcl_order_service( io_repo = NEW zcl_order_db( ) ).  " real DB in a unit test
ENDMETHOD.
```
**Why this is wrong:** it's slow, non-deterministic (depends on data), can't run everywhere, and isn't a *unit* test.
**Correct approach:** inject a double; reserve real-resource tests for separate integration tests with the appropriate risk level.

**Mistake #2: Asserting on incidental detail / multiple unrelated things.**
```abap
METHOD everything FOR TESTING.
  " ...10 asserts on formatting, totals, logging, side effects in one method...
ENDMETHOD.
```
**Why this is wrong:** a failure doesn't say what broke; the test is fragile to unrelated changes.
**Correct approach:** one behaviour per test method, named for the behaviour; assert the essential outcome.

## 8. Comparison With Similar Concepts

**Stub vs Spy vs Mock:** a *stub* feeds canned inputs (state verification — assert the result); a *spy* records what it received (assert afterwards what was called); a *mock* sets expectations up front and fails if they aren't met (interaction verification). Choose by whether you care about the *result* or the *interaction*.

**Hand-written double vs `cl_abap_testdouble`:** hand-written gives full control and is dependency-free but is more code; the framework removes boilerplate for interfaces and supports argument matchers and call verification. Use the framework for nontrivial interfaces.

**Test seam vs dependency injection:** DI is the clean, designed way to substitute dependencies; **test seams** (`TEST-SEAM`/`TEST-INJECTION`) and the double framework's ability to replace global/static calls are *retrofitting* tools for legacy code you can't easily refactor to inject. Prefer DI; use seams as a bridge.

**How this works with:**
- **ADT (Eclipse):** run tests with Ctrl+Shift+F10; view the ABAP Unit results; coverage measurement is built in.
- **gCTS / CI pipelines:** ABAP Unit runs automatically on transport/CI; abapGit projects test in pipelines.

- **`cl_abap_testdouble` / `cl_osql_test_environment` / `cl_cds_test_environment`:** framework doubles for objects, Open SQL, and CDS, enabling DB-free tests.

**SAP-Specific Considerations:** local test classes live in the global class's *test include*, keeping tests with the code but out of production runtime. Use `RISK LEVEL`/`DURATION` honestly; `HARMLESS` tests must not change persistent data. Befriend the test class (Topic 2.11) only when white-box access is truly needed.

## 10. Anti-Patterns & Gotchas

**Anti-Pattern: testing implementation instead of behaviour.**
```abap
" asserting that a private helper was called in a certain order, not that the OUTCOME is right
```
**Why this fails:** the test breaks on harmless refactors and doesn't protect the actual contract.
**Correct approach:** assert observable behaviour through the public API; let internals change freely.

**Common Gotcha:** shared static state (Topic 2.2) and singletons (Topic 3.2) leak between tests because they survive the session. Reset them in `setup`, or inject fresh instances, or your tests will pass/fail depending on execution order.

## 11. Testing & Validation

**How to Verify Understanding:** Can your test run with no database/RFC/UI, fail for exactly one reason, and read as Given/When/Then? If it needs real infrastructure or asserts many unrelated things, it isn't a clean unit test.

**Unit Test Example (spy: interaction verification):**
```abap
" A SPY double records the message it was asked to send:
CLASS ltd_notifier DEFINITION.
  PUBLIC SECTION.
    INTERFACES lif_notifier.
    DATA mv_last TYPE string.
ENDCLASS.
CLASS ltd_notifier IMPLEMENTATION.
  METHOD lif_notifier~notify.
    mv_last = iv_text.                      " record, don't really send
  ENDMETHOD.
ENDCLASS.

CLASS ltcl_checkout DEFINITION FOR TESTING DURATION SHORT RISK LEVEL HARMLESS.
  PRIVATE SECTION. METHODS checkout_notifies FOR TESTING.
ENDCLASS.
CLASS ltcl_checkout IMPLEMENTATION.
  METHOD checkout_notifies.
    DATA(lo_spy) = NEW ltd_notifier( ).
    DATA(lo_cut) = NEW zcl_checkout( io_repo     = NEW ltd_repo( )
                                     io_tax      = NEW ltd_tax( )
                                     io_notifier = lo_spy ).
    lo_cut->checkout( '4711' ).
    cl_abap_unit_assert=>assert_not_initial( lo_spy->mv_last ).   " a notification was sent
  ENDMETHOD.
ENDCLASS.
```
**Test Explanation:** the spy verifies an *interaction* (a notification was sent) without sending real email — interaction testing made possible by injecting the double.

## 12. Quick Reference Summary

**Key Takeaways:**
- ABAP Unit: local `FOR TESTING` classes, `setup`/test methods, `cl_abap_unit_assert`, Given/When/Then, one behaviour per test.
- Isolate the unit with doubles — hand-written (stub/spy/mock) or `cl_abap_testdouble`-generated for interfaces.
- Injection (Topic 3.5) is what lets doubles in; test seams retrofit legacy code; reset shared state.

**When to Apply:** all nontrivial business logic — and as the safety net before any refactor.

**Red Flags:** real DB/RFC in unit tests; manual `WRITE`-and-look "tests"; asserting internals; many unrelated asserts; tests sensitive to execution order.
